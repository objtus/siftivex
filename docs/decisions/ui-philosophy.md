# UI 設計思想 — 資料探し・リスト中心

> **状態**: 草案（2026-09-06）— モック v2 / React 実装の前に確定する
> **参照**: [blueprint.md](../../blueprint.md) §画面, §UIパーツ, §デバイス・レスポンシブ設計

## 目的

Siftivex の UI は **資料探し（参照画像の発見・比較・枝分かれ探索）** を最優先する。

作画参考アーカイブとして、次のループを **同等に重要** として扱う:

1. タグ / 自然言語で絞る → リストをスクロール → 候補を詳細で確認
2. 絞る → 1 枚開く → **ホイール**で連続確認
3. 絞る → 気に入った 1 枚から **類似還流** → 枝探索 → **パンくず**で戻る

専用画面・専用タスクを増やさず、**イメージリスト（順序付き image_id 集合）** と **クエリ** に処理を集約する（blueprint の統一モデル）。

## 表示とデータ — ルート非依存（2026-09-06）

UI の表示ロジックは **ルート名（`route_tag`）を前提にしない**。

現在は pixiv と under 系など少数のルートしかないが、ルートは増える可能性がある。under 系にも将来 `image_metadata` 相当の情報が付くかもしれない。**データの状態に合わせて表示を切り替える** のが基本方針とする。

### 原則

| 原則 | 内容 |
|---|---|
| **データ駆動** | フィールドの有無・値で表示を決める。ルート ID で分岐しない |
| **汎用性優先** | 新ルート追加時に UI 分岐を増やさない設計をデフォルトとする |
| **ルート最適化は慎重に** | 特定ルート向けの特例・分岐・ラベル固定は **選択して** 入れる。安易な `if (route === …)` は避ける |

「pixiv なら作品名」「under ならファイル名」のような **ルート前提の表示表** は作らない。代わりに **メタデータがあれば作品情報として出す。なければファイル名にフォールバック** する。

### API と UI の責務分離

詳細コンテキストは次の **2 種類のデータ** を区別する（どちらもルート非依存）:

| データ | 意味 | 表示への影響 |
|---|---|---|
| **`metadata`** | この画像について分かっている構造化情報（title, artist, posted_at, source_url 等） | タイトル・サブ行。1 枚でも返す |
| **`work`** | 同一作品に複数ページがあるときの **副次ナビ用** コンテキスト | ページストリップ・`[` `]` ナビ。**2 枚以上あるときのみ** |

```
タイトル  ← metadata.title ?? file_name
サブ行    ← metadata の各フィールド（なければ解像度等のフォールバック）
ページナビ ← work が存在し page_count > 1 のときのみ
```

ルートは **ファイル情報**（共通メタデータの「ルート」行）として表示するだけ。表示分岐の条件には使わない。

### ルート向け最適化を入れるとき

次のような場合のみ、ルート固有の処理を **明示的に選んで** 入れる:

- ルートごとに **データ形状が根本的に違い**、汎用フィールドに無理やり載せると UX が悪化する
- ルート専用の **取り込みパイプライン** に合わせた表示が、資料探しで明確に有利
- 汎用実装を試したうえで、足りないと判断した

入れるときは **モックまたは spec で理由を残す**。「今あるルートが pixiv と under だから」だけでは採用しない。

## 統一モデル（blueprint 継承）

### イメージリストが中心

- 画面上の「今の作業対象」= 現在のクエリが生成した **イメージリスト**
- タグ・自然言語・OCR・アルバム・類似還流はすべて **同じクエリ言語** 上のフィルタ
- 並び替え（ファイル名 / 関連度 / 類似軸）は **リストの順序** を変えるだけ

### 還流と起点履歴

類似画像・モチーフ・色味などを **フィルタに還流** するとき:

- 新しいクエリで **リストが差し替わる**（blueprint の `similar_to:` 等）
- **OriginBreadcrumb（起点スタック）** で還流前のクエリに戻れる（目安: 直近 5 件）
- 「類似を起点に昇格」ボタンで、枝探索の結果を新しい正本リストにできる

**スクロール位置復元**（要検討・望ましい）:

- パンくずで起点に戻ったとき、可能なら **リストのスクロール位置も復元**
- 実装コスト・複雑度に依存。セッション内保持を第一候補とし、無理なら Phase を後ろにずらす

### 類似画像の二つの使い方（両方）

| 使い方 | 動作 |
|---|---|
| **詳細内** | 詳細を開くと類似リストが表示。クリックでその作品の詳細へ（リスト順とは独立） |
| **還流** | 「色味 / 時期 / モチーフでリストを更新」→ クエリ変更 + 起点スタックに積む |

## イメージリストと詳細 — 二層ナビ（確定方向）

**リストのフィルタリング** と **詳細画面のナビ** は **別レイヤ** として考える。

### リスト層（画像単位）

- フィルタ結果は常に **画像 1 枚 = 1 行**（フラット）
- ある作品の **全ページがリストに載るとは限らない**（タグはページごとに異なりうる）
- 167p まとめがタグ検索に大量ヒットする場合も、**原則フラット表示**（どのページがヒットしたか分かるように）
- 作品単位への畳み込み（`group:work`）は **未定** — 必要なら後から表示モードとして追加

### 詳細層（閲覧・副次ナビ）

- リストで画像をクリック → 詳細は **その image_id** を表示
- **リスト順 ←→** : 現在の **フィルタ済みイメージリスト** 内の前後（blueprint 準拠）
- **作品ページナビ**（pixiv 等）: フィルタ結果に関係なく、**同一 work_id の全ページ** へ移動できる副次 UI
  - UI: ページストリップ + `p3 / 43` 等
  - 実装: 内部的には `work_id` で取得したページ集合（API: `GET /api/works/{id}/pages`）
  - **イメージリストのフィルタとは独立** — 「リストに無いページ」も詳細から辿れる

```
[ フィルタ済みリスト ]          [ 詳細 ]
  img A  ←→ img C  ←→ img F       表示: img C
  （作品 X の p2 のみ）            副次: X の p0…p42 全部へジャンプ可
```

### `work:` クエリ（将来・P2）

- **作品単位でリストを絞る** トークンとして `work:12345` を想定
- **特定ページ指定**（`page:3` 等）は **不要** — 1 枚だけ見るならクエリではなく詳細で指定すればよい
- Phase 2 では **副次ナビのみ** で足りる。`work:` はリストに「作品の全ページを並べたい」ときの拡張

## PC レイアウト（要検討 — 選択肢）

資料探し優先。blueprint の「3 ペイン常時表示」と、「フィルタ画面と画像表示を分ける」案の **両方** を doc 上に残し、モック v2 前に決める。

### 案 A — 3 ペイン常駐（blueprint そのまま）

```
┌──────────┬─────────────────────┬──────────────┐
│ TagPicker│   ImageList         │  DetailPane  │
│ Query    │   (grid / table)    │  preview     │
│ Breadcrumb│                    │  tags/OCR    │
└──────────┴─────────────────────┴──────────────┘
```

- 長所: リストと詳細を常に見比べられる
- 短所: プレビューが小さくなりがち

### 案 B — 探索 ⇔ 閲覧のモード切替

```
探索モード:  左フィルタ + リスト全幅（詳細はサムネのみ or 非表示）
閲覧モード:  大プレビュー + メタ + 副次ナビ（Esc で探索へ、スクロール位置復元）
```

- 長所: 資料の「じっくり見る」に最適
- 短所: モード切替の実装・状態管理

### 案 C — リスト上オーバーレイ詳細

- リストを維持したまま詳細を被せ、閉じると **同一スクロール位置** に戻る
- 短所: タグ編集・類似還流 UI の置き場

**現時点（2026-09-06）**: **試してから決める**。モック v2 で案 A・B を切替比較し、資料探しの体感で選ぶ。案 C は必要なら後から追加。

### モック v2 で試すこと

| 比較軸 | 案 A（3ペイン） | 案 B（探索⇔閲覧） |
|---|---|---|
| リストの見え方 | 常時・中央 | 探索時フル幅 |
| プレビュー | 右ペイン（やや小） | 閲覧モードで大きく |
| フィルタ | 左常駐 | 探索モードで左、閲覧時は非表示 or 最小 |
| 戻り | — | Esc → 探索 + スクロール位置（試作） |
| 副次ナビ | 右ペイン上部 | 閲覧モード上部 |

Layout Lab に **レイアウト preset: A / B** を追加する想定。

### PC で確定していること

| 項目 | 方針 |
|---|---|
| 主リスト | グリッド + 詳細リストの **両方**（切替） |
| 詳細リスト | 小サムネ + ファイル名 / タグ / OCR 抜粋（blueprint） |
| 左ペイン | QueryInput + TagPicker + OriginBreadcrumb |
| キーボード | `/` 検索、`←→` リスト順、ホイール = 詳細で前後 |

## クエリ UI

- **QueryInput** は常時編集可能（`tag:`, `-tag:`, 自然言語, 将来 `album:`, `similar_to:`, `work:`）
- **TagPicker** の循環ボタンと **双方向同期**
- 複雑な入れ子クエリは chip に完全反映されない → **控えめな注記**（blueprint）
- 自然言語とタグを **別入力にするか単一欄にするか** — Phase 2 では **単一 QueryInput** で開始（裏側ハイブリッド）

## 作品ページ・メタデータ — API と UI の対応

| レイヤ | API | UI |
|---|---|---|
| リスト | `GET /api/images?q=…` | フラット。ページは独立行 |
| 詳細 — 表示 | `GET /api/images/{id}` → **`metadata`** | タイトル・作者・投稿日等（1 枚でも。ルート非依存） |
| 詳細 — 副次ナビ | `GET /api/images/{id}` → **`work`** | 複数ページがあるときのみ |
| 副次ナビ | `GET /api/works/{id}/pages` | ページストリップ（リストフィルタと独立） |

pixiv は現時点で `metadata` の主な供給源だが、**UI は pixiv 専用ではない**。他ルートが同フィールドを持てば同じ見え方になる。
